<discretion_resolutions>
- **`StandardScaler().set_output(transform="pandas")` inside a `Pipeline` for both linear learners.**
  This is substantive, not cosmetic, and 04-RESEARCH §Q2 measured all three reasons. First, unscaled
  `LogisticRegression` at sklearn's default `max_iter=100` does **not** converge on this design —
  a 200-shuffle null loop would then be a null distribution of half-optimized models. Second, the
  scaled pipeline converges in 9 iterations against 173 and fits about ten times faster
  (0.0068 s versus 0.068 s). Third and most important for correctness: `history` ranges over roughly
  $30 to $3,346 while the one-hot columns are 0/1, so an L2 penalty on the unscaled design barely
  touches the `history` coefficient — **the "regularized linear learner" D-10 names is not actually
  regularized without scaling.**
- **`.set_output(transform="pandas")` on the scaler is required, not optional** (04-RESEARCH §Q2, and
  04-RESEARCH Pitfall 3). With a plain `StandardScaler()` the scaler emits a NumPy array and the final
  estimator does not receive `feature_names_in_` — `hasattr(pipeline[-1], "feature_names_in_")` is
  `False` while `hasattr(pipeline, ...)` is `True`. A criterion-2 assertion written against the inner
  estimator would then either raise `AttributeError` or, far worse, compare `None == None` and pass
  vacuously.
- **One `_score` dispatch, not a `kind=` parameter or a class hierarchy** (04-RESEARCH §Q4). The
  estimator already carries the information: `hasattr(model, "predict_proba")` is `True` for the
  classifier pipeline and `False` for the Ridge pipeline, and sklearn's `available_if` correctly
  declines to expose the method through a `Pipeline` wrapping a regressor — verified on sklearn 1.9.0.
  A `kind` parameter duplicates information the object holds; a class hierarchy is three files of
  ceremony for one branch.
- **`n_jobs` is a literal `1`, never `-1`** (04-RESEARCH §Q1). `n_jobs=-1` emits a `UserWarning` from
  `sklearn.utils.parallel` on this version, which is noise in a repo whose suite is clean, and
  thread-count-dependent floating-point reduction order is a reproducibility hazard for a *committed*
  artifact. The 6.4-minute full-null budget is acceptable for a once-per-build step.
- **`random_state` is a fixed literal `20260902` on every forest.** sklearn's default is `None`. If it
  varied across the 200 shuffles, the permutation null would confound "the label carries no
  information" with "the bootstrap and feature-subsampling draws differ", and the resulting
  distribution would be wider than the hypothesis being tested (04-RESEARCH §Q5 subtlety 5).
</discretion_resolutions>
