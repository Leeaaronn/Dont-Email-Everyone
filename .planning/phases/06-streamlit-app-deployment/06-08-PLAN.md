<objective>
Put it on the internet, from a recorded configuration, and write the link down.

Purpose: APP-02 and ROADMAP criterion 5. There is one piece of state in this entire project that
does not live in git — the Community Cloud app record (repo, branch, entrypoint path, Python
version, custom subdomain), which lives in Streamlit's dashboard at `share.streamlit.io`. If the
entrypoint path ever moves, the deployed app breaks with no repo-side signal. That is the argument
for choosing the entrypoint path once, at the repo root, before the first deploy — which 06-04 did —
and for recording the exact deployed values in the phase summary so the deployment is reproducible.

Community Cloud deployment has no CLI and no public API: it is a browser flow at
`share.streamlit.io` authenticated through GitHub. That makes the deploy step one of the rare cases
where a human action genuinely cannot be automated. Everything around it is automated here: the
readiness gate, the parameter set, the README edit and the test that guards the link.

Output: a live public URL, a recorded deployment tuple, and the link in the README with a test
behind it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub remote → Community Cloud build | Cloud installs and executes whatever the pushed repo declares |
| Community Cloud dashboard → the deployment | The one piece of project state outside git |
| Public URL → any visitor | No authentication; anyone can open, use and screenshot the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-31 | Tampering | Cloud selecting a different dependency file than the verified one | mitigate | `test_no_competing_dependency_file_exists` asserts no `uv.lock`, `Pipfile` or `environment.yml` exists, and the deploy checkpoint requires the build log to be inspected for the four banned packages — the failure mode is silent, so it is caught by looking rather than by the app failing. |
| T-06-32 | Information disclosure | Everything in the repo becoming world-readable through the deployment | accept | The dataset is the public Hillstrom 2008 experiment, vendored and checksummed; the repo is already public per project memory; there is no PII beyond the published columns, no secret, no `.env` and no `st.secrets`. Recorded so a later change that adds private data knows it is crossing this boundary. |
| T-06-33 | Elevation of privilege | Deployment credentials | mitigate | Deployment is a GitHub OAuth browser flow performed by the repo owner; no token, key or secret is committed, and `st.secrets` is on the forbidden element list precisely so the deployment adds no state outside git. |
| T-06-34 | Denial of service | A public app on a free tier | accept | Read-only over 170,718 bytes of committed files, no upload, no unbounded input; hibernation after 12 hours is the platform's own throttle and is documented in the README rather than fought. |
| T-06-35 | Repudiation | The dashboard record drifting from the repo | mitigate | The exact tuple (repo, branch, entrypoint, Python version, subdomain) is recorded in the plan summary, and the entrypoint was fixed at the repo root before the first deploy specifically so it never has to move. |
</threat_model>
